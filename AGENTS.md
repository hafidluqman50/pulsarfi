## 1. Directory Infrastructure & Zero-Tolerance Boundary Policy

Never violate the repository directory structure or place files in unauthorized directories.

### 1.1 Backend (`backend/`)
- **`backend/src/`**: **STRICTLY PRODUCTION CODE ONLY**.
  - **ABSOLUTELY FORBIDDEN** to place test files (`*_test.go`), temporary scripts, scratch tests, or mock files inside `backend/src/` (including `backend/src/service/...`, `backend/src/http/...`, `backend/src/repository/...`, `backend/src/app/...`, etc.).
  - There are zero exceptions for any reason.
- **`backend/test/`**: **ALL TESTS LIVE HERE**.
  - All automated testing, unit tests, live integration tests, and benchmark Go files MUST reside inside `backend/test/...` (e.g. `backend/test/service/agent/...`).

### 1.2 Frontend (`frontend/`)
- **`frontend/components/`**, **`frontend/app/`**, **`frontend/http/`**: Production components, hooks, API clients, and application routes.
- Frontend test files (if any) are strictly restricted to `frontend/__tests__/`.

### 1.3 Smart Contract (`smart-contract/`)
- **`smart-contract/src/`**: Production Solidity source code only.
- **`smart-contract/test/`**: ALL Foundry test files (`*.t.sol`) MUST reside in `smart-contract/test/`.
- Do not edit files under `smart-contract/lib/**`. Treat Uniswap dependencies as read-only.

### 1.4 Documentation & Workplanning (`docs/`)
- **`docs/plans/`**: Work plans, architectural specifications, and technical changelogs.

## 3. ABSOLUTE BAN: ZERO HARDCODED LANGUAGE IN DYNAMIC RESPONSES (100% USER-DRIVEN DYNAMIC LANGUAGE)

> [!CAUTION]
> **ABSOLUTELY FORBIDDEN:**
> It is strictly forbidden to hardcode ANY text for dynamic responses from the LLM in ANY language (neither Indonesian, English, nor any other language) anywhere across the codebase.
> All agentic chat responses, footnote reminders, cancellation replies, confirmation card labels, button text, and clarifying questions **MUST BE 100% DYNAMICALLY GENERATED BY THE LLM** matching the exact language used by the user.

### Rules of Language Enforcement:
1. **Dynamic Language Mirroring:**
   - Detect and mirror 100% the active language or dialect used by the user in the chat thread (Indonesian, English, Javanese, Turkish, Japanese, etc.).
   - If the user interacts in Indonesian -> 100% consistent Indonesian in chat prose and interactive cards.
   - If the user interacts in English -> 100% consistent English in chat prose and interactive cards.
   - If the user interacts in Japanese -> 100% consistent Japanese in chat prose and interactive cards.
   - And so on for any language or dialect the user initiates.
2. **Zero Hardcoded Response Fallbacks:**
   - Never append or inject static string templates in Go code (such as `reminder := "\n\n*Catatan: ...*"`, `cancelReply := "Trade plan cancelled..."`, or `content := "Perhatian Horizon: ..."`).
   - If a reminder, cancellation notice, or horizon card needs to be presented, the backend **MUST invoke the LLM** (or pass instructions into the active LLM turn) to generate the content and labels dynamically in the user's active language.
3. **System & Non-Agentic Errors:**
   - **ALL ERRORS OTHER THAN AGENTIC ERRORS IN CHAT MUST BE IN ENGLISH!**
   - Smart contract reverts, low-level RPC/network errors, database failures, transaction toast notifications, wallet errors, and non-chat modal UI errors MUST remain in standard English.
4. **No Language Mixing:**
   - Never force a single static language or mix languages outside the boundaries specified above.

## 4. Frontend Contract Simulation (`simulateContract`)

- Every on-chain contract call from the frontend (such as ERC-20 `approve`, swap, or task arming) **MUST** be pre-flight simulated using `publicClient.simulateContract`:
  ```typescript
  const { request } = await publicClient.simulateContract({ ... });
  await writeContractAsync(request);
  ```
- Calling `writeContractAsync` directly without simulation is strictly prohibited.
- Catch and cleanly format simulation errors before triggering wallet confirmation popups (MetaMask).

## 5. Project Core Philosophy & Token Model

PulsarFi is an Asset-Backed Tokenization Platform (Real World Assets / RWA) on Arbitrum Sepolia that tokenizes Indonesian IDX equities (BUMIP, ENRGP, BRPTP, etc.) into 1:1 on-chain receipts paired against IDRX liquidity pools.

### Fundamental Rules:
- **Asset-Backed, NOT Synthetic.** Every token minted represents actual shares held 1:1 in custody at KSEI. Price discovery comes from AMM mechanics and arbitrage, not external oracles.
- **USDC Compliance Model.** Anyone can hold and swap tokens permissionlessly (no upfront KYC). KYC is enforced only at the Redemption Gateway when converting tokens back to physical securities.
- **Token Naming Convention:** All asset tokens use ALL-CAPS with a `P` suffix indicating Pulsar origin:
  - Valid: `BUMIP`, `ENRGP`, `BRPTP`, `PTROP`, `BBRIP`, `BMRIP`, `BBCAP`, `BDMNP`.
  - Forbidden: `pBUMI`, `pENRG`, `PBUMI`, `PENRG`.
- **Decimals:**
  - IDRX decimals = 2 (matches real IDRX).
  - PulsarStock decimals = 18.
  - Amounts stored in database as `NUMERIC(78,0)` (raw on-chain uint256).

## 6. Architecture & System Design

### 6.1 Smart Contracts (`smart-contract/`)
- **`PulsarProtocol.sol`** — UUPS upgradeable proxy, single entry point for protocol operations.
  - Mint 3/5 multisig: `requestMint` -> `approveMint` -> `executeMint` (creates V4 pool and seeds full-range liquidity on first mint).
  - Redeem 3/5 multisig: `requestRedeem` -> `approveRedeem` -> `executeRedeem`.
  - `swapV4(ticker, amountIn, amountOutMin, buyStock)` — permissionless spot swaps.
- **`PulsarProtocolOps.sol`** — delegatecall target for less-hot-path functions to comply with EIP-170 code size limit.
- **`v4/PulsarSwapHook.sol`** — Uniswap V4 hook enforcing protocol fee (`swapFeeBps`) in IDRX at the pool level.
- **`PulsarStock.sol`** — Independent ERC-20 token per stock, deployed lazily on first `executeMint`.
- **`AgentTaskManager.sol`** — Self-custodial AI trade execution manager. Enforces on-chain guardrails:
  - `totalBudget`: budget ceiling.
  - `maxAmountPerTrade`: per-tranche ceiling for DCA/standing orders.
  - `cooldownInterval`: minimum seconds between executions.
  - Decoupled decimals: IDRX base units (`10^2`) for Buy, Stock base units (`10^18`) for Sell.
- **AMM:** Uniswap V4 (official `PoolManager`) is the sole live venue. Spot swaps only; no limit orders or order types.

### 6.2 Backend Engine (`backend/`)
- Go + Gin + GORM + PostgreSQL + CloudWeGo Eino.
- Directory structure: `src/{app,auth,config,http,logger,model,repository,service}`.
- **AI Agent System (Quasar / Nova / Comet):**
  - **Supervisor (Quasar):** Conversational entry point, routes requests, handles clarification questions, auto-settles direct trades.
  - **Analyzer (Nova):** Technical analysis, news synthesis, stock charts, portfolio snapshots.
  - **Executor (Comet):** On-chain execution, sizing calculation, spot swaps via `AgentTaskManager`.
- **Dynamic Task Scheduler (`scheduler_service.go`):**
  - Evaluates standing orders when cooldown elapses.
  - Proactively pushes H-1 horizon expiry notice with dynamic language-aware card contracts.

### 6.3 Frontend App (`frontend/`)
- Next.js (App Router) + TailwindCSS + RainbowKit + Wagmi.
- Use Tailwind utility classes for styling. Preserve existing visuals 1:1.
- Permanent `<ChatThread />` mounting via CSS visibility to preserve WebSocket streaming and progress state across tab navigation.

## 7. Planning Mode Guidelines

When asked to create an implementation plan (Planning Mode), follow these rules strictly:
1. **No code during Planning Mode.** Do not modify code or run state-changing commands until the user has approved the plan.
2. **Version every plan document — zero tolerance.**

   > [!CAUTION]
   > **ABSOLUTE, ZERO-TOLERANCE RULE: every single edit to a plan document bumps the version and adds a changelog row. No exceptions, no matter how small.**
   > This applies to a wording tweak, a corrected field name, a fixed line in a wireframe, a reordered question, a one-sentence clarification — anything, however minor or "obvious." There is no such thing as a change too small to log. A plan document with an edit that has no matching changelog row is a broken audit trail, full stop. If you are unsure whether something counts as an edit, it counts.
   - Bump MINOR for any content revision (wording, detail, ordering, a fixed mistake). Bump MAJOR only when the approach/scope changes enough that the prior plan is no longer valid.
   - Every changelog row states which section changed and what changed in it, specific enough that a reader never has to diff the file to know what happened.
3. **English only.** Plan documents are written entirely in English.
4. **Required Sections:** Problem Statement, Definition of Done, Feature Description, Impacted Files, UI/UX Changes (Lo-Fi), Flowchart, Verification Plan.
5. Header format, immediately followed by the changelog table (present from `1.0` onward, not just once the document reaches its second revision):
   ```markdown
   # <Feature Name>

   | | |
   |---|---|
   | **Version** | 1.0 |
   | **Status** | Draft |
   | **Date Created** | YYYY-MM-DD |
   | **Last Updated** | YYYY-MM-DD |

   | Version | Date | Change |
   |---|---|---|
   ```
